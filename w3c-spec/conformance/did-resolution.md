# DID Resolution Conformance Matrix (0.6 Evidence)

**Standards baseline:** [DID Resolution v1 Candidate Recommendation Snapshot, 06 August 2026](https://www.w3.org/TR/2026/CR-did-resolution-1.0-20260806/). **Integration base:** `55dde88ce1e451587303b5f4fc388eef4bdb32f5`. **Implementation under test:** the exact clean `git HEAD` printed by `pnpm test:conformance`, not the integration base.

**Overall 0.6 compatibility result: FAIL.** The current package exposes a DID Core 1.0-era bare-document `resolve(did)` plus separate result and representation helpers. The pinned CR instead requires the unaltered `resolve(did, resolutionOptions)` contract, uses `application/did`, requires URL-typed structured error objects in the normative resolution algorithm, and returns a null DID Document for a deactivated DID. Version 0.6 keeps keyword errors, old media types, split helpers, and a readable deactivated document. These are disclosed compatibility failures, not 0.6 passing claims. The coordinated breaking migration is tracked by [#447](https://github.com/midnightntwrk/midnight-did/issues/447).

This matrix covers the package-level resolver callback boundary, not an HTTP resolver service and not a concrete indexer transport implementation. Restricted passes are retained only for method-specific lookup/projection and metadata components that can be reused behind a future conforming interface. Exact revision evidence comes from clean-tree command output recorded in PR or release evidence; this lane is not currently run or retained by CI. Immutable external/CI evidence remains tracked by [#446](https://github.com/midnightntwrk/midnight-did/issues/446).

The distinction between the error requirements is important: the normative algorithm in §4.4 requires an error object whose `type` is the specified W3C URL. Section 11 says implementations **SHOULD** use RFC 9457 to encode that error data structure. RFC 9457 encoding is therefore a SHOULD; returning the algorithm's structured URL-typed error object is not optional. Version 0.6 returns keyword strings instead.

## Trust interpretation

The injected reader's response is trusted input to this package resolver. A stale, unavailable, compromised, or untrusted read does not prove DID absence, deactivation, or transaction finality. Applications needing independent state integrity or finality must supply it above this profile; 0.6 provides no light client, state-proof verification, or independent consensus check.
