## PR #110 Review — `feat(api): guard DID examples and managed artifacts`

### Overview

Three coherent additions:

1. **Runnable API examples** — `packages/api/examples/deploy-did.ts` + `update-did.ts` replace a single markdown snippet with two TS files compiled by a new `tsconfig.examples.json` and exercised by `npm run typecheck:examples`. Wired into `run-api.sh`.
2. **Managed-artifact freshness guard** — new `scripts/managed-artifact-catalog.mjs` exposes a profile catalog (`contract`, `jubjub-schnorr`) with `--json`, `--check`, `--check-catalog`, `--explain`, `--ready`, `--build-command`, `--profile-names` modes. Wired into `ci:core` between contract build and domain build.
3. **Surface-discipline expansion** — `check-did-surface-discipline.mjs` now asserts `check:managed-artifacts`/`typecheck:examples` are exposed, `examples/**` is in the api package `files` list, and `run-api.sh` invokes the typecheck.

Net diff is additive (+499/−9, 14 files); no runtime code touched.

### Code Quality & Correctness

**Catches a real gap.** Without this guard, generated Compact outputs (`packages/contract/src/managed/...`) silently go stale across `did.compact` edits — they are checked into the repo but otherwise unverified. The input set (`*.compact`, `package.json`, `scripts/`) is the right granularity.

**Mostly clean. A few small concerns:**

- `packages/api/examples/update-did.ts:73-76` — the new example does `await updateService(didContract, { ...service, serviceEndpoint: "..."})`, bypassing `createService` and therefore skipping `normalizeServiceEndpoint`. The prior `deploy-and-update.md` correctly re-wrapped the spread in `createService(...)`. As a teaching example this is a regression: it implies "spread-and-update" is the supported pattern, when consumers should re-validate. Recommend mirroring the markdown form:
  ```ts
  await updateService(didContract, createService({ ...service, serviceEndpoint: "..." }));
  ```

- `packages/api/examples/README.md:11,23` — `node --loader ts-node/esm` is deprecated since Node 20 (`ExperimentalWarning: --loader is deprecated, use --import`). Either switch to `tsx examples/deploy-did.ts` (already in root devDeps via ts-node only — would need adding) or document `node --import 'data:text/javascript,import { register } from "node:module"; import { pathToFileURL } from "node:url"; register("ts-node/esm", pathToFileURL("./"));' examples/deploy-did.ts`. Quick win: `tsx`.

- `scripts/managed-artifact-catalog.mjs:78` — `stat.mtimeMs + 1 < newestInput` tolerates only 1 ms skew. Modern macOS APFS and Linux ext4/xfs have ns precision so it's fine in practice, but `git clone` resets all mtimes to clone time, which means a fresh checkout that hasn't rebuilt will report *every* artifact as stale — fine because the guard is positioned after the build steps in `ci:core`, but a developer running `check:managed-artifacts` directly after `git clone` will see confusing failures. A one-line note in `README.md` ("run after a build, not after a fresh clone") would help, or the script could detect missing outputs vs. stale outputs distinctly in the error message (it already separates them internally — surface that to the operator).

- `scripts/managed-artifact-catalog.mjs:138` — `workspaceScriptMatch` regex `/^npm run ([^\s]+) -w \.\/(.+)$/u` only validates the `npm run X -w ./packages/Y` form. If a future profile uses `npm run -w ./packages/Y X` (flag-first) or `npm --workspace=...`, the catalog will silently accept it without verifying the script exists. Low risk today (`check:did-surface-discipline` constrains shape), but a `--check-catalog` test fixture would harden this.

- `scripts/managed-artifact-catalog.mjs:155-176` — `--explain` / `--ready` / `--build-command` exit 2 on unknown profiles; `--check` exits 1 on errors; `--json` defaults silently. The mixed exit codes are sensible but undocumented. Adding `Usage:` text with exit-code conventions in a comment or `--help` mode would help downstream consumers.

- `scripts/managed-artifact-catalog.mjs:175-176` — `case "--json": case undefined:` makes the no-arg behavior equal to `--json`, which is a friendly default but also means a typo in the flag silently falls through to the default block (no — it goes to `default`, which exits 1). Actually the switch is correct. Disregard.

- `packages/api/tsconfig.examples.json` — doesn't `extends` the base `tsconfig.json`. Duplicates `strict`, `target`, `module`, `lib`, etc. Drifting silently between the two configs is a hazard. Consider `"extends": "./tsconfig.json"` with overrides only for `include`, `noEmit`, `declaration: false`, `composite: false`.

- `packages/api/eslint.config.mjs:25` — adding `tsconfig.examples.json` to `parserOptions.project` is correct for type-aware rules on `examples/**`, but the config file doesn't declare a separate `files: ["examples/**/*.ts"]` block. ESLint will apply the same rule set to examples as to `src`, which is fine, but verify `unused-vars` / `no-console` etc. don't fire on example-specific patterns (the examples use `console.log`, which presumably passes the existing config — easy to confirm by running `npm run lint -w ./packages/api` locally).

- `packages/api/examples/deploy-did.ts:9-11` & `update-did.ts:22-30` — pre-condition checks throw plain `Error` with helpful messages. Good. The bigintReplacer is duplicated across both files; a `_shared.ts` next to them would avoid the copy-paste, but two-line duplication is below the threshold for extracting a helper. Leave it.

### Tests & Validation

- The PR description lists eight validation commands. All are present in `package.json` / `run.sh`. Two of those (`check:managed-artifacts`, `check:run-target-catalog`) are also gated by `ci:core`, which is good.

Given the 270-line surface area and multiple modes, at least a smoke test (similar to `scripts/run-sh-contract.test.mjs`) for `--check-catalog` and `--explain <unknown>` exit codes would prevent regressions. Not a blocker — the surface-discipline guard catches the most likely breakage (rewiring `ci:core` or removing the script entry).
